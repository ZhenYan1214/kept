> 暫定名稱：**Kept（守諾）**：讓災難善款的承諾無法被改寫，讓該拿到的人不被遺漏。
> 參賽組別：Tech Track（獨立參賽）｜初賽截止：2026/10/25（目標 10/24 晚上前送出）

## 1. 要解決的兩個根本問題（皆有真實事件佐證）

| # | 問題 | 國際案例 | 台灣案例 |
|---|---|---|---|
| **P1** | **善款承諾可以被事後改寫**：先募款、後規劃，結餘被挪作他用，捐款人與災民都無從制衡 | 海地紅十字會：4.88 億美元只蓋 6 棟房屋；瓦倫西亞 DANA：善款一年後才發放 | 0403：一年後仍剩 4.2 億，委員會沒有災民；0206：檢調搜索；高雄氣爆：59 個項目都沒寫用途依據 |
| **P2** | **不知道錢該給誰，最需要的人被漏掉**：沒有共用的受災者名冊，各單位各自認定資格 | 日本紅十字會：手上 1,740 億日圓，卻「無法確認」該發給誰 | 光復：各機關受災戶數不一（1,606／1,837／2,582）、三村被排除、一樓重災戶多次落空、NGO 等名冊等了兩個月 |

**一句話動機：** 花蓮人不是不想捐，是不敢再捐。信任崩壞的代價，由下一次的災民承擔。

## 2. 設計原則（從真實失敗中學到的）

1. **區塊鏈縮到最小、但不可或缺。** 只把「承諾、決議、資格的匿名紀錄、發放與簽收」放上鏈；個資一律不上鏈。
2. **個資零上鏈。** 鏟子英雄個資外洩是反面教材，鏈上只存匿名識別碼與雜湊。
3. **承諾由程式碼強制執行，不靠事後揭露。** 用途上限、結餘政策、改變用途的程序都寫進合約。
4. **災民有發言權。** 改變用途時必須有災民代表簽核，並設公開冷靜期。
5. **長輩也能用。** 可以印成紙本 QR 憑證卡（參考日本能登地震時用 Suica 卡登記避難者），不需要手機、App 或助記詞；受災戶不付 gas，由中繼者代送交易。
6. **人工判斷要可追責。** 村長或公所的資格認定無法完全自動化，但「誰認定了誰、誰被拒、申訴多久被處理」要公開可查。

## 3. 角色

| 角色 | 真實對應 | 在系統中做什麼 |
|---|---|---|
| **基金保管方** | 賑災基金會、縣府專戶 | 建立善款基金，宣告用途承諾；撥款給發放方案 |
| **監督委員會** | 善款委員會（**至少一位災民代表**） | 多簽核准撥款與用途變更 |
| **捐款人** | 一般民眾、企業 | 捐款、取得收據、追蹤款項流向、收到變更通知 |
| **資格簽發方** | 鄉鎮公所、村長 | 將受災戶加入資格群組（依受災等級分級）、處理申訴 |
| **受災戶** | 災民（含租屋者、未設籍者） | 持有匿名憑證；用零知識證明申領、確認收到、提出申訴 |
| **發放方** | NGO、基金會、縣府窗口 | 建立發放方案，驗證證明後撥款 |
| **公眾／稽核者** | 媒體、議員、監察院 | 查看公開儀表板 |

## 5. 智能合約設計

### 5.1 `ReliefFund`（處理 P1：讓承諾無法被改寫）
- **建立時就寫死的承諾：**
  - `categories[]`：用途類別與比例上限，例如：生活慰助 ≤ 60%、房屋修繕 ≤ 30%、心理與社區重建 ≤ 10%
  - `sunsetDate`：預定結案日
  - `surplusPolicy`：結餘的去向，例如：只能用於同一災區的長期重建，**不得轉作其他災害或公共工程**
  - `committee`：委員名單、門檻 M-of-N，以及**必須包含災民代表的簽核**
  - `timelock`：改變用途的公開冷靜期，例如 7 天
- **函式：**
  - `donate(amount, category?)`：捐款（可指定用途）並發出收據事件
  - `fundProgram(programId, category, amount)`：委員會多簽後撥款給發放方案；**超過該類別上限就會被合約擋下**
  - `proposeReallocation(from, to, amount, reasonURI)`：提案改變用途 → 公開冷靜期 → 必須有災民代表簽核才能 `execute`
  - `settleSurplus()`：到期後依 `surplusPolicy` 處理結餘，**任何人都能觸發**
- **事件：** `Donated`、`ProgramFunded`、`ReallocationProposed`、`ReallocationExecuted`、`SurplusSettled`

### 5.2 `EligibilityRegistry`（處理 P2：受災資格）
- **可信簽發者名單**：公所或村長的地址，以及他們負責的轄區（村代碼）
- **Semaphore 群組**：每場災害、每個受災等級一個群組，例如 `全倒`、`半倒`、`淹水`
  - 簽發者把受災戶的**身分承諾（identity commitment）**加入群組；鏈上只看得到一個雜湊值
  - 每一筆加入紀錄都標註**是哪位簽發者加入的**，方便追責
- **申訴：**
  - `fileAppeal(villageCode, evidenceHash)`：例如「我家淹水但不在紅區」
  - `resolveAppeal(id, accepted, reasonURI)`
  - 儀表板公開各村的申訴數量與平均處理天數。**三村事件會在第一天就被看見，不必等到陳抗。**
- **撤銷**：資格認定錯誤時可以移除，並留下紀錄

### 5.3 `AidProgram`（發放與送達證明）
- 由發放方（NGO 或基金會）建立：`category`、`eligibleGroup`、`amountPerHousehold`
- `claim(proof, nullifier, recipient)`：
  - 驗證 Semaphore 證明，確認申領者屬於符合資格的群組
  - nullifier 以「災害 ID」為範圍，所以**同一戶在同一場災害裡有一個固定的匿名戶號**
    - 同一方案不能重複領取 → **防重複**
    - 可以跨方案統計「這個匿名戶號領過哪些方案」 → **找出被遺漏的人**
    - 公眾和其他單位都無法把匿名戶號對應到真實身分
- `confirmReceipt(proof)`：受災戶用同一個身分簽收，證明**錢或物資真的送到了**，而不只是撥款而已
- 實物或修繕補助：廠商上傳發票雜湊，受災戶簽收後才撥款給廠商

> **隱私邊界（簡報時要誠實說明）：** 發放方撥款到銀行帳戶時一定會知道收款人是誰。本系統保證的是：**公眾、其他單位、甚至簽發的公所，都無法從鏈上資料反推出誰領了什麼。**

## 6. 前端（一個 Next.js 應用，依角色分頁）

| 頁面 | 使用者 | 重點功能 |
|---|---|---|
| `/fund/new` | 基金保管方 | 建立基金與承諾，用表單產生合約參數 |
| `/donate` | 捐款人 | 捐款、收據、「我的善款去了哪裡」（按比例追蹤） |
| `/issuer` | 公所／村長 | 掃描受災戶的 QR 加入群組、選擇受災等級、處理申訴 |
| `/wallet` | 受災戶 | 建立身分（存在手機，或印成紙本 QR 卡）、查看可申領的方案、一鍵申領、簽收、申訴 |
| `/distributor` | NGO | 建立方案、查看申領與簽收狀況 |
| `/committee` | 委員會 | 簽核撥款或用途變更（災民代表也有獨立入口） |
| `/` 儀表板 | 所有人 | 見下方 |

**公開儀表板（簡報的主畫面）：**
- **承諾與實際對照**：每個用途類別的上限、已撥、已送達（已簽收）
- **覆蓋缺口**：已認證的受災戶 X 戶，其中 **Y 戶一個方案都還沒領到**（一樓重災戶的故事）
- **申訴地圖**：各村待處理的申訴數量與天數（三村的故事）
- **用途變更紀錄**：每一次提案、冷靜期倒數、誰簽了、災民代表是否同意（0403 的故事）
- **結餘倒數**：距離結案日還有幾天、還剩多少、依承諾將流向哪裡
- （加分）**AI 預警**：例如「此基金撥款進度落後，與 0403 的模式相似」

| 層 | 選擇 | 理由 |

## 8. Demo 劇本（每一幕都對應一個真實事件）

模擬場景：**「花蓮光復 2025 堰塞湖」重演**

1. **建立基金**：基金會宣告承諾，用途上限、結餘只能用於同一災區、委員會含災民代表 → *對應高雄 59 項無用途依據*
2. **捐款湧入**：多位捐款人捐款，儀表板即時更新
3. **公所認證**：公所把受災戶加入「全倒」「淹水」群組；**南富村一戶不在名單上** → 提出申訴 → 儀表板亮紅燈 → 公所受理並加入 → *對應三村「次等災民」*
4. **一次證明，多處申領**：受災戶用同一個匿名身分，向基金會領「家園復原」、向 NGO 領「生活物資」 → *對應 NGO 等名冊等了兩個月*
5. **重複申領被擋下**：同一戶再領一次 → 交易失敗 → *防重複*
6. **找出被遺漏的人**：儀表板顯示「3 戶已認證但尚未領到任何方案」 → *對應一樓重災戶多次落空*
7. **簽收**：受災戶確認收到 → 「已撥款」變成「已送達」
8. **試圖挪用**：保管方提案把結餘轉去「縣府工程」 → 合約直接拒絕（違反結餘政策）；改提案轉到其他用途 → 進入 7 天公開冷靜期，**災民代表沒有簽核就無法執行** → *對應 0403 的 4.2 億*
9. **結案**：時間到，任何人都能觸發結餘結算，依承諾流向長期重建

## 9. 落地路徑與誠實面對的限制（評審一定會問）

| 質疑 | 回應 |
|---|---|
| 台灣捐款多是台幣，不是加密貨幣 | **第一階段**：善款仍在銀行，鏈上記錄承諾與決議，每一筆撥款附銀行交易憑證雜湊，由會計師共同簽署；**第二階段**：《虛擬資產服務法》（2026/6/30 三讀）的子法上路後，改用合規的台幣穩定幣直接進合約。已有前例：Binance Charity 的 117,210 USDT 捐入賑災基金會 |
| 保管方在鏈下說謊怎麼辦？ | 這正是第一階段的限制；但「承諾、決議、用途變更」的公開紀錄已經大幅提高說謊成本。第二階段金流上鏈後，由合約強制執行 |
| 資格認定是人做的，資料錯了上鏈也沒用（garbage in） | 不假裝能解決；改成讓**人的判斷可追責**：誰認定、誰被拒、申訴多久處理，全部公開 |
| 個資法 | 鏈上沒有個資；法務部 102 年函釋認為，政府提供名冊給慈善團體「僅供發放之用」可能合法，本系統連名冊都不必傳 |
| 誰會用？ | 試點對象：賑災基金會（受衛福部監督、已承諾每週公開，最有動機）；參考日本的被災者台帳制度 |
| 長輩不會用 | 紙本 QR 卡、村長或社工代為操作、無須 gas |
| 手機或卡片在災害中遺失 | 簽發者可以撤銷舊身分、重新簽發，鏈上留紀錄 |
